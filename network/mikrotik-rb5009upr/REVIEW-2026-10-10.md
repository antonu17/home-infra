## Findings requiring follow-up

### IPv6 policy does not implement the VLAN isolation policy

Home has a global IPv6 router address and Cloud a ULA router address. ND is
configured for both. The existing IPv6 input and forward policies finish with
`drop in-interface-list=!LAN`, rather than default deny for all unmatched traffic.
All five internal VLAN interfaces belong to LAN. Consequently unmatched internal
IPv6 traffic falls through and is accepted: Cloud/Home routing can bypass the
IPv4 inter-VLAN policy, and internal IPv6 router management is not restricted to
Home. The existing bad-address filters do not exclude these legitimate prefixes.
Guest or IoT manually using IPv6 is also not covered by equivalent zone policy.

Prepare an explicit IPv6 policy before claiming full segmentation. Preserve
ICMPv6, WAN DHCPv6, existing Thread routes and required network services; do not
resolve this by blindly deleting defconf IPv6 rules or disabling IPv6.

### MAC management still includes Guest, IoT and Cloud

MAC server and MAC WinBox use `allowed-interface-list=LAN`. LAN includes Guest,
IoT, Cloud and infrastructure management in addition to Home. Neighbor discovery
also uses LAN. The IPv4 input chain does not enforce MAC management restrictions.
Keep LAN for routed classification and separately prepare a Home-only MAC
management policy if that is the intended administration boundary. This review
does not alter those settings.

### ExternalDNS permissions do not currently provide an effective allowance

`EXTERNALDNS-EGRESS` has no entries, so the active scoped HTTP80 rule cannot
match. The separate HTTPS443 rule from 192.168.40.40 follows the input terminal
deny and is unreachable. Documentation describes HTTP as the operator's current
endpoint but also contains an HTTPS procedure. The actual workload endpoint is
secret-backed, and was not read. Confirm endpoint/port and observed source before
preparing the active exception. Do not infer actual egress from a node address
merely because an old example rule used it.

Cilium values enable BGP and Kubernetes IPAM but do not explicitly configure
masquerading or native-routing CIDRs. Installed defaults, workload placement,
SNAT and Pod source visibility need runtime evidence. HA has the same uncertainty.

### Git BGP address-list entries are stale

Live export BGP-PEERS: .40.21/.40.40/.40.41/.40.42. `07-address-lists.rsc` still
adds .40.21/.40.22/.40.23/.40.40. Reimport would add .22/.23 and retain .41/.42,
leaving an inaccurate list used for both BGP input and Home Talos management.
Reconcile the source to actual peers before reapplying 07. Do not change the
existing BGP connections or erase potentially planned control-plane addresses
from unrelated documentation.

### NAS access is limited to the documented web services

The Home NAS rule is now correct for HTTP(S), Pi-hole8081 and ping. It does not
allow direct DSM5000/5001, SMB445, SSH22, NFS or other NAS services. Confirm which
are actually used before adding narrowly scoped ports. Vault8200 is documented
as a loopback backend behind the HTTPS reverse proxy and should remain private.
Cloud-to-NAS .40.5 traffic is same-VLAN switching; RouterOS routed firewall does
not isolate it, or distinguish Kubernetes Pods from other Cloud hosts.

Two historical Cloud-to-NAS/PXE rules still target .100.5. The legacy DNS rules
still target .100.2, while current router upstream DNS is .40.5. Verify retirement
of those old endpoints before removing the exact rules; those rules cannot make
an absent old address usable. The export alone does not prove Synology/CSI,
registry, factory or Pi-hole availability or upstream configuration.

### Several prepared exceptions are inactive

PRINTERS, INFRA-MGMT, HA-EGRESS, HA-IOT, EXTERNALDNS-EGRESS and
REMOTE-MGMT-SOURCES have no entries. Their rules cannot match. REMOTE has no
interface members, so remote management is not configured by this package.
No RouterOS Tailscale interface/container configuration appears in this export.
A Tailscale subnet router elsewhere could SNAT traffic into a local zone; confirm
its path before claiming preserved remote access.

VLAN1 infrastructure has no initiation-to-Internet allowance and no DNS-to-router
allowance. Aruba can be managed from Home only after INFRA-MGMT is populated.
If the AP uses router DNS, NTP, cloud services or updates, its required flows need
verification and narrow exceptions. Management-device connectivity was not
validated by the export.

### Additional TFTP entry has an address typo

Three scoped PXE entries use 192.168.40.0/24. A fourth, uncommented entry uses
192.160.40.0/24 for ipxe-x86_64.efi. This is outside the Cloud subnet. Correct
bootstrap entries remain present, so the typo alone does not prove PXE failure.
Review the exact duplicate before removing it. TFTP service ownership is outside
this RouterOS package; no TFTP changes are made in this review.

### Comment refresh files have not all been reapplied

The export still has old bridge, bridge-port, VLAN, gateway and interface-list
comments. NAT already has its new comment. Source files03/05/06/10 assign the new
comments. This is cosmetic drift, not evidence that VLAN configuration is absent.
The newly supplied pool export resolves the previous unknown pool ranges; source
still deliberately preserves existing ranges rather than enforcing them.
